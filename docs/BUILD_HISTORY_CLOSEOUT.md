## 为什么仍未达标

样板首次记录中，场景构建约2.59秒、GPU准备约1.59秒（其中纹理上传约1.09秒），另外还有入口脚本、静态数据和纹理就绪开销。GPU的编译等待与纹理上传有重叠，`textureUploadMs`属于`compileMs`内的子阶段，不能重复相加。仅减少索引分配和重叠上传还不能保证原画质下稳定5秒内完成。

导演仍在“等待当前计算结束 → 验证完整海区历史与静态地形 → 恢复区域 → 发布”这条串行流程上等待。第3章开始播放后的首条完成窗口诊断为24.31秒，其中历史13.43秒、静态确认9.11秒；后续记录的完整窗口约4.12–7.85秒，其中历史约3.32–5.75秒。首章还记录到约5秒的队列/屏障等待。合并旧复合检查中的重复条件未解决完整流程的成本。

这些是不同已完成窗口的诊断，不能当作每次可见停顿的精确分解；转章加载期间的“最近完成窗口”还可能来自上一请求。本轮不把缓存复用或后台计算等同于等待消失。更改这条流程需要另立有边界的工程任务，本轮停止，不自动继续修补。
